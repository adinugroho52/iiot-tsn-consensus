Byzantine consensus and a control loop on one TSN path

A walkthrough of a packet-level ns-3 study comparing the Time-Aware Shaper, strict priority, and FIFO when a PBFT committee shares links with a periodic control flow.

Press → or click a step above. Every number on these pages comes from release v1.2.0 of the simulator.

The model

A programmable logic controller sends a control frame every 1000 µs to an I/O device across a chain of switches.

A committee of validators hangs off the same switches, round-robin, so its traffic crosses the trunk links the control frame uses.

Each port runs one discipline. TAS gives control and consensus separate time windows; strict priority and FIFO have no gates.

Change the chain and committee to see where the consensus load concentrates.

This is a real capture from trunk port sw1 → sw2 while 16 validators exchange 1024-byte messages every 2 ms, far more than the consensus window can carry.

Along the path

With a narrow 5 µs control window, each hop's window must open as the frame arrives. The aligned schedule delays the window by one frame time per hop.

The naive schedule opens every window at the same instant. The frame arrives a little later at each hop, and at hop 6 the window has already closed.

Theory against simulation

Under aligned TAS, the last of B back-to-back control frames should arrive after (B−1)·τc + Nh·hc, whatever the consensus traffic does.

The window holds ⌊Wc/τc⌋ frames, and the deadline allows ⌊(D−Nhhc)/τc⌋+1.

Three disciplines

Sixteen validators exchange 1024-byte messages every 10 ms while the control burst grows.

The table gives the largest burst that meets the deadline with nothing late or lost. TAS follows its formula at every path length; strict priority loses ground as the deadline tightens and the path grows.

Consensus sees the opposite ordering. At 1 Gb/s its commits take about three times as long under TAS; at 100 Mb/s the TAS window cannot carry this load at all.

Reproducibility

The model is deterministic. With no random option set, a configuration always produces the same result, so one run per configuration is enough and differences are exact.

All 697 runs, plus the capture runs, were executed on an Intel Xeon and an AMD Ryzen machine. Every log, per-frame record, and capture was byte-identical.

The release ships the SHA-256 of every output, so a rerun anywhere is checked automatically.
